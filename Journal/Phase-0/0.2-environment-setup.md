## WHY (Rationale)

### Docker Compose for Local Development
**Reasoning:**
- Consistent development environment across team members
- Easy infrastructure startup (`docker-compose up`)
- Matches production architecture
- Isolated from host system
- Health checks ensure services are ready before app starts

**Trade-off:** Requires Docker, but it's industry standard

### Multi-Profile Configuration
**Reasoning:**
- `dev`: Verbose logging, auto-reload, relaxed security for development
- `test`: Separate database, optimized for test execution
- `prod`: Minimal logging, strict security, optimized performance

**Implementation:** Spring Boot's `@SpringProfile` annotation

### HikariCP Connection Pooling
**Settings:**
- Max pool size: 10-20 connections per service
- Connection timeout: 20s
- Idle timeout: 5 minutes
- Max lifetime: 20 minutes

**Reasoning:**
- HikariCP is fastest, most reliable pool
- Prevents connection exhaustion
- Optimized for PostgreSQL

### Redis for Caching & Rate Limiting
**Reasoning:**
- In-memory speed for feature flag evaluation
- Atomic operations for rate limiting
- TTL support for cache invalidation
- Persistence with AOF (append-only file)

### Prometheus + Grafana
**Reasoning:**
- Industry-standard metrics stack
- Real-time monitoring
- Alerting capabilities (future phase)
- Custom business metrics support

### Environment Variables
**Reasoning:**
- 12-factor app methodology
- Secrets don't live in code
- Easy configuration per environment
- Container-friendly

## TECHNICAL DECISIONS

### Decision 1: PostgreSQL Over MySQL
**Reasoning:**
- Superior JSON support (for log metadata)
- Better full-text search (for log aggregation)
- Advanced indexing (GIN, GiST)
- Proven scalability
- Strong ACID compliance

**Alternative Considered:** MySQL - lacks advanced features we need

### Decision 2: Redis Persistence (AOF)
**Configuration:** `appendonly yes`

**Reasoning:**
- Rate limit counters shouldn't be lost on restart
- Feature flag cache can rebuild from DB
- AOF provides durability without performance hit

**Alternative:** RDB snapshots - less durable

### Decision 3: Actuator Endpoints Exposed
**Exposed:**
- `/actuator/health` - Service health checks
- `/actuator/info` - Build and version info
- `/actuator/metrics` - Application metrics
- `/actuator/prometheus` - Prometheus format metrics

**Reasoning:**
- Essential for monitoring and observability
- Prometheus scraping requires /prometheus endpoint
- Health checks for load balancers

**Security Note:** In production, restrict access via Spring Security

### Decision 4: JWT for Authentication
**Configuration:**
- 256-bit secret (minimum for HS256)
- 24-hour access token expiration
- 7-day refresh token expiration

**Reasoning:**
- Stateless authentication
- Scales horizontally
- No session storage needed
- Standard for microservices

**Alternative:** Session-based - doesn't scale well

### Decision 5: CORS Configuration
**Dev:** `allowed-origins: "*"` (all origins)
**Prod:** Specific domain whitelist

**Reasoning:**
- Dev: Convenience for local frontend development
- Prod: Security - only trusted origins

### Decision 6: Flyway Over Liquibase
**Reasoning:**
- Simpler SQL-based migrations
- Better PostgreSQL support
- Easier to review in PRs
- Baseline-on-migrate for existing DBs

**Will implement in Phase 0.3**

### Challenge 1: Gradle Wrapper Generation Network Issue
**Problem:** Network restrictions preventing download of Gradle distribution in sandboxed environment

**Solution:**
- Documented proper command: `gradle wrapper --gradle-version 8.5`
- Created placeholder gradlew script
- In real environment with network access, wrapper generation would succeed
- Project structure and configuration are correct

**Learning:** Development environment setup assumes network access to repositories

### Challenge 2: Port Allocation Strategy
**Problem:** Choosing ports that don't conflict with common services

**Solution:**
- Gateway: 8080 (standard HTTP alternate)
- Services: 8081-8085 (sequential, easy to remember)
- Avoided: 3000 (frontend), 5432 (Postgres), 6379 (Redis), 9090 (Prometheus)

### Challenge 3: Database Pool Sizing
**Problem:** How many connections per service?

**Solution:**
- Gateway: 20 (highest traffic)
- Service Registry: 10 (moderate)
- Others: 10-15 based on expected load
- Formula: `connections = (core_count * 2) + effective_spindle_count`
- Can tune based on actual metrics later

**Learning:** Start conservative, optimize based on production metrics
