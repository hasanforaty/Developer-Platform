## WHY (Rationale)

### Multi-Module Architecture
- **Separation of Concerns**: Each service handles a specific domain (registry, logs, feature flags, etc.)
- **Independent Deployment**: Modules can be deployed and scaled independently
- **Shared Code Reuse**: Common-lib prevents code duplication across services
- **Development Efficiency**: Teams can work on different modules in parallel

### Technology Choices

**Kotlin as Primary Language:**
- Modern, concise syntax reduces boilerplate
- Null safety prevents NPE errors
- Excellent Spring Boot integration
- Coroutines support for async operations (future use)
- Industry standard for modern JVM applications

**Spring Boot 3.2.0:**
- Latest stable version with modern features
- Native support for GraalVM (future optimization)
- Improved observability with Micrometer
- Virtual threads support (Project Loom)
- Production-ready features (actuator, metrics, health checks)

**Gradle with Kotlin DSL:**
- Type-safe build configuration
- Better IDE support and code completion
- Consistent with application language (Kotlin)
- Faster builds compared to Maven
- Better dependency management

**Java 17:**
- LTS (Long Term Support) version
- Modern JVM features (records, pattern matching, text blocks)
- Better performance compared to Java 11
- Required for Spring Boot 3.x

## TECHNICAL DECISIONS

### Decision 1: Gradle Over Maven
**Reasoning:**
- Faster incremental builds
- More flexible and powerful
- Better support for multi-module projects
- Kotlin DSL provides type safety

**Trade-off:** Gradle has steeper learning curve, but benefits outweigh costs

### Decision 2: Separate Module per Service (vs Monolith)
**Reasoning:**
- Aligns with microservices architecture
- Enables independent scaling
- Teams can own specific modules
- Clear boundaries between services

**Trade-off:** More complexity in local development, but manageable with Docker Compose

### Decision 3: Common-lib as Non-Bootable Library
**Reasoning:**
- Contains only shared code (no main method needed)
- Prevents accidental execution as standalone app
- Proper JAR packaging for library consumption

**Implementation:**
```kotlin
tasks.getByName<BootJar>("bootJar") { enabled = false }
tasks.getByName<Jar>("jar") { enabled = true }
```

### Decision 4: Package Naming Convention
**Pattern:** `com.devplatform.<module-name>`

**Reasoning:**
- Clear, consistent structure
- Module name in package prevents conflicts
- Easy to navigate codebase
- Follows Java/Kotlin best practices

### Decision 5: Service-Specific Spring Features
Each service enables only what it needs:
- `service-registry`: `@EnableScheduling` for health checks
- `log-aggregation`: `@EnableAsync` for async log processing
- `feature-flag-service`: `@EnableCaching` for flag evaluation caching

**Reasoning:** Principle of least privilege - only enable features you use
