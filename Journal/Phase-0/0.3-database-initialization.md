## WHY (Rationale)

### Flyway for Database Migrations
**Reasoning:**
- Version control for database schema
- Repeatable deployments
- Baseline support for existing databases
- SQL-based (easy to review and understand)
- Automatic migration on startup

**Alternative Considered:** Liquibase - more complex XML/YAML format

### Soft Delete Pattern
**Implementation:** `deleted_at TIMESTAMP NULL`

**Reasoning:**
- Audit trail preserved
- Can restore accidentally deleted services
- Historical data remains queryable
- Foreign key integrity maintained

**Trade-off:** Queries must filter `deleted_at IS NULL`

### JSONB for Flexible Data
**Used in:**
- Service instance metadata
- Log entry metadata
- Feature flag user segments
- Experiment configurations
- API usage details

**Reasoning:**
- Schema flexibility without migrations
- Native PostgreSQL querying with GIN indexes
- Better than TEXT (JSON validation)
- Efficient storage

### GIN Indexes for Search
**Used in:**
- Log message full-text search
- JSONB metadata queries

**Reasoning:**
- Fast text search without Elasticsearch
- Native PostgreSQL feature
- Good for log aggregation use case
- Lower operational complexity

### Multi-Tenant Ready Design
**Approach:**
- Service-name based partitioning
- No hard-coded tenant IDs (yet)
- Easy to add tenant_id column later

**Reasoning:**
- Current use case: single deployment
- Future-proof for multi-tenancy
- Service isolation via service_name

### Pre-Aggregated Statistics
**Tables:**
- `log_statistics` (daily counts)
- `api_usage_statistics` (hourly metrics)
- `experiment_results` (calculated results)

**Reasoning:**
- Real-time queries on raw data are slow
- Pre-aggregation speeds up dashboards
- Batch jobs can calculate during off-hours
- Balance between storage and query performance

## TECHNICAL DECISIONS

### Decision 1: Separate Database vs Shared Database
**Choice:** Shared database with separate schemas per service

**Reasoning:**
- Simpler local development (one PostgreSQL)
- Services are in same trust boundary
- Cross-service joins possible if needed
- Can split later if needed

**Production Note:** Can use separate databases per service in production

### Decision 2: BIGSERIAL for Primary Keys
**Choice:** `BIGSERIAL` instead of `SERIAL` or `UUID`

**Reasoning:**
- Auto-incrementing (simple, fast)
- 64-bit range (9 quintillion rows)
- Better performance than UUID
- Sequential disk writes (InnoDB-friendly)

**Alternative:** UUIDs - better for distributed systems, but slower

### Decision 3: Timestamp Precision
**Choice:** `TIMESTAMP` without timezone

**Reasoning:**
- Application handles timezone conversion
- All timestamps in UTC (by convention)
- Simpler querying
- Spring Boot @CreatedDate uses UTC

**Convention:** Application always stores/retrieves UTC

### Decision 4: Index Strategy
**Approach:**
- Primary keys (automatic)
- Foreign keys
- Query-specific indexes (service_name, timestamp)
- Composite indexes for common queries
- GIN indexes for JSONB and full-text

**Reasoning:**
- Balance between write performance and query speed
- Indexes based on expected query patterns
- Can add more based on production metrics

### Decision 5: Constraint Naming
**Pattern:** `chk_` for check constraints, `uq_` for unique, `idx_` for indexes

**Reasoning:**
- Easy to identify constraint type in errors
- Consistent with PostgreSQL conventions
- Makes debugging easier

### Decision 6: Enum Values in CHECK Constraints
**Example:** `CHECK (status IN ('UP', 'DOWN', 'DEGRADED'))`

**Reasoning:**
- Enforces data integrity at database level
- Self-documenting
- Prevents invalid values
- Can add values with ALTER later

**Alternative:** Separate enum tables - more flexible but overkill

### Decision 7: Auto-Update Triggers
**Implementation:**
```sql
CREATE FUNCTION update_updated_at_column()
CREATE TRIGGER update_users_updated_at BEFORE UPDATE
```

**Reasoning:**
- Application doesn't need to set updated_at
- Guaranteed consistency
- PostgreSQL handles it automatically
- One place to maintain logic

## CHALLENGES & SOLUTIONS

### Challenge 1: Reusing update_updated_at_column Function
**Problem:** Function defined in service-registry, but other services need it

**Solution:**
- Each service runs its own migrations
- Function defined in first migration of each service
- Acceptable duplication for microservice independence
- Alternative: shared migration module (adds complexity)

**Decision:** Duplicate function definition in each service

### Challenge 2: Cross-Service Foreign Keys
**Problem:** Feature flags might reference services, but different databases in prod

**Solution:**
- Use VARCHAR service_name instead of BIGINT service_id
- Denormalized but microservice-friendly
- Application enforces referential integrity
- Works across database boundaries

**Learning:** Microservices avoid database-level foreign keys across services

### Challenge 3: Log Volume Management
**Problem:** Logs can grow to millions of rows quickly

**Solutions Implemented:**
1. Retention policies table
2. Indexes on timestamp for fast deletion
3. Pre-aggregated statistics
4. Future: Table partitioning by timestamp

**Next Phase:** Implement cleanup jobs

### Challenge 4: API Usage Table Growth
**Problem:** High-traffic APIs generate millions of rows

**Solution:**
- Hourly pre-aggregation
- Raw data retention policy (7 days)
- Indexes optimized for time-range queries
- Future: Partitioning by month

### Challenge 5: Experiment Results Calculation
**Problem:** Statistical calculations are expensive

**Solution:**
- Store calculated results in `experiment_results`
- Batch calculation job (future phase)
- Cache results for dashboard
- Recalculate on-demand if needed
